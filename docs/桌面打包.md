# 桌面打包说明

所有命令在项目根目录执行。建议使用 Node.js 22 LTS、Corepack 和项目指定的 Yarn；macOS 在 Mac 上构建，Windows x64 在 Windows x64 上构建。输出目录为 `release/desktop/`，安装包不包含用户 SQLite 数据。

## 首次准备

```sh
corepack yarn install --immutable
```

检查 `node_modules/electron/dist` 是否已有运行时；若安装时未执行 Electron 下载脚本，运行：

```sh
node node_modules/electron/install.js
```

首次准备需要网络。这一步下载宿主平台的 Electron；之后本机打包显式指定该目录，避免构建器独立下载同版本运行时。升级项目 Electron 版本、切换平台或架构后，需要准备对应的新运行时。不要随意修改 Electron 版本来绕过下载，也不要使用其他机器遗留的、不匹配的平台目录。

## macOS 架构与系统要求

Intel Mac 使用 `mac-x64`，Apple Silicon 使用 `mac-arm64`。当前 Electron 44 最低要求 macOS 13；macOS 12 或更早不能靠更换 CPU 架构解决。配置显式写入最低系统版本 13.0。

```sh
# 一次生成 Apple Silicon + Intel 两套 DMG／ZIP
corepack yarn desktop:dist:mac
# 仅 Intel Mac（也可在 Apple Silicon 上交叉打包）
corepack yarn desktop:dist:mac:x64
# 仅 Apple Silicon
corepack yarn desktop:dist:mac:arm64
```

上述根命令会构建最新源码。Apple Silicon 运行时直接复用本机已安装的 `node_modules/electron/dist`，Intel x64 运行时由构建器单独下载／缓存；两次构建使用各自架构的运行时。产物文件名含 CPU 架构，两个包分别安装，不是 universal 单一包。

## macOS 本机运行时复用命令

zsh / bash：

```sh
# 源码改动后构建；Web 页面与主进程都会更新
corepack yarn desktop:build

# 复用本机已安装的 Electron，生成本机架构 DMG + ZIP
corepack yarn workspace @mydoc/desktop dist:mac --config.electronDist="$PWD/node_modules/electron/dist" --publish never
```

采用绝对路径，因为构建器从桌面子包解析相对路径。命令不指定 CPU 架构，按当前构建环境选择；本地运行时必须与该架构一致。Apple Silicon 的原生 arm64 环境生成 arm64 包，Intel 的 x64 环境生成 x64 包；在 Rosetta 下要确认 Node 与安装运行时的架构。

仅需本机可运行 `.app`、不需要安装包时，使用以下命令，省去 DMG / ZIP 压缩：

```sh
corepack yarn workspace @mydoc/desktop run package:dir --config.electronDist="$PWD/node_modules/electron/dist" --publish never
```

前提是已经运行 `desktop:build`，且之后没有修改源码。只改打包配置、重复生成同一份代码时，可跳过再次构建。

## 应用图标

图标主图为 `assets/branding/mydoc-icon-v1.png`。侧栏和浏览器标签页分别使用 Web `public/` 下的 `mydoc-icon.png`、`favicon.png`；桌面 `resources/` 提供 `icon.icns`（macOS）、`icon.ico`（Windows）和 `icon.png`（运行时）。桌面构建会把运行时 PNG 复制到 `dist/`，用于窗口及 macOS Dock。

更换主图后，在 macOS 上运行 `node scripts/generate-app-icons.mjs` 重新生成上述资源，再执行 `corepack yarn desktop:build` 和对应平台打包命令。生成资源应随源码保存，Windows 打包无需安装图标转换工具。已有安装包不会随资源修改自动更新，需要重新打包并安装。

## Windows x64 推荐命令

在 Windows x64 PowerShell 中执行：

```powershell
corepack yarn desktop:build
$mydocElectronRuntime = (Resolve-Path "node_modules/electron/dist").Path
corepack yarn workspace @mydoc/desktop dist:win --config.electronDist="$mydocElectronRuntime" --publish never
```

只需要应用目录而不生成 NSIS 安装程序时：

```powershell
$mydocElectronRuntime = (Resolve-Path "node_modules/electron/dist").Path
corepack yarn workspace @mydoc/desktop run package:dir --config.electronDist="$mydocElectronRuntime" --publish never
```

Windows 打包目标固定 x64；Windows ARM 环境安装的 arm64 Electron 不能直接用于这些命令，应另行准备 Windows x64 运行时。Mac 上的 `node_modules/electron/dist` 是 macOS 运行时，不能拿它打 Windows 包。

## 双架构与跨平台构建

macOS 同时生成 Apple Silicon / Intel 包：

```sh
corepack yarn desktop:build
corepack yarn workspace @mydoc/desktop dist:mac --arm64 --x64 --publish never
```

双架构根命令会先用本机 arm64 运行时，再让构建器为 x64 下载／缓存 Intel 运行时。**不要把 arm64 的 `electronDist` 传给 x64**：自定义目录会直接复制运行时，不能自动将 arm64 转成 x64，可能导致产物架构标识与实际可执行文件不一致。

跨平台构建也需要对应目标平台运行时及打包工具；推荐使用 `.github/workflows/desktop.yml` 在 macOS / Windows 分别构建和测试。首次运行仍会下载，交叉打包成功不代表安装运行验收通过。

## 打包慢的排查

打包分为源码构建、获取运行时、复制／封装应用和生成安装包。此前本机 Web 构建约 9 秒，不能把随后数分钟的等待都视作前端编译。

- 日志停在下载、网络连接仍活跃而 CPU 较低：通常在等待运行时或打包工具下载。默认构建器下载／缓存与项目已安装目录是两条路径；按推荐命令显式传入 `electronDist`。已有卡住的任务可先 Ctrl+C 停止，再重新执行，避免两个任务同时写同一输出目录。
- 日志出现 `using custom unpacked Electron distribution` 和 `copying unpacked Electron`：已复用本地运行时，不再下载 Electron；后续仍可能获取首次使用的 DMG／NSIS 等工具。这不是完全离线模式。
- 日志进入 `building target=DMG` / `macOS zip` / `nsis`：正在制作与压缩安装包。Electron 自带运行时体积较大，Mac 默认还生成两种产物；本地测试优先使用应用目录命令。
- 只需重做安装包但代码未变：直接运行桌面子包命令，跳过 `desktop:build`；改了源码则必须先重新构建，避免打出旧页面。

原有根命令 `desktop:dist:mac`、`desktop:dist:win`、`desktop:pack` 会自动重建源码，但未指定本地运行时，采用默认下载／缓存流程。日常本机打包优先使用本文命令。其中 `desktop:dist:mac` 现已显式生成 arm64 + x64 两套包；指定单架构用 `desktop:dist:mac:x64` 或 `desktop:dist:mac:arm64`。CI 分别在 Apple Silicon 与 Intel runner 上测试并构建对应包。

## 完成与分发

等待命令成功退出后，再使用 `release/desktop/` 中的最终安装包。失败／中断期间，应用目录可能尚未完整，旧安装包也可能仍在，不以文件存在判断本次成功。

本地默认是未签名开发包；正式分发使用独立 `desktop:release:mac`／`desktop:release:win` 命令，签名／公证、手动 CI 与更新渠道配置参见 [桌面发布](./桌面发布.md)。当前不配置发布渠道，普通开发包禁用在线更新。数据库初始化及用户数据目录行为不受打包命令影响，不能把个人数据库复制进安装包。

## 文件关联与打开文件验收

安装包配置声明 `.md` / `.markdown` 为 Markdown 文档（macOS Editor 角色，Windows NSIS 注册关联）。开发模式直接运行 Electron 不等于系统已注册 MyDoc 文件关联；验证双击行为需要使用安装后的应用，并在系统“打开方式”中选择 MyDoc。

验收顺序：退出应用后打开 Markdown，确认只显示导入预览、取消不写入；应用已运行时再打开另一份文件，确认复用窗口；当前弹窗未结束时再打开文件，确认排队而不是覆盖；同文件再次确认导入，默认跳过已导入内容。Windows 还需在实机验证安装／卸载关联与带空格中文路径。未签名安装包的系统确认行为沿用平台规则。

源代码验证已覆盖 macOS Electron 启动参数、菜单、open-file 处理与真实第二进程交接；Windows 注册配置与交叉打包检查不能替代 Windows 实机验收。文档深链协议不包含在此文件关联中。


## 文档协议验收

安装新版本后，macOS 检查应用 `Contents/Info.plist` 的 `CFBundleURLTypes` 包含 `mydoc`；Windows 安装器注册 `mydoc` URL Protocol。使用从同一安装版文档复制的链接测试冷启动和已有窗口唤起，核对正文块／画框定位、弹窗期间延后处理及不存在文档提示。macOS 可使用 `open 'mydoc://document?workspace=实际ID&doc=实际ID&mode=page'`；Windows 可在运行窗口粘贴链接。系统出现应用选择时选择 MyDoc。

开发版本不注册默认协议，避免夺取正式安装版的链接处理权；开发数据库与安装版数据库不同，不要拿开发文档 ID 验证安装版数据定位。构建配置和原生事件测试不能替代 Windows 实机安装与默认协议验收。


## 防止文件名与实际架构不符

所有 macOS 打包入口共用 `afterPack` 架构检查：压缩／签名前读取应用主程序、Frameworks 中真实 Mach-O 头，核对目标 CPU。误把 arm64 运行时传给 x64 时直接失败，不生成该架构安装包。不要仅根据 `mac-x64` 文件名判断可用性。检查现有包可用：

```sh
lipo -archs release/desktop/mac/MyDoc.app/Contents/MacOS/MyDoc
lipo -archs "release/desktop/mac/MyDoc.app/Contents/Frameworks/Electron Framework.framework/Versions/A/Electron Framework"
```

Intel 包均应包含 `x86_64`。如果输出 `arm64`，删除错误的安装包分发副本后重新打包；不得只改名。原生模块后续若被引入，还需要针对目标架构构建，不能复制另一架构的模块。

当前 SQLite 使用 Electron 内置 `node:sqlite`，随目标 Electron 运行时提供，不依赖本机 `better-sqlite3` 二进制。开发依赖仍用于 Web 服务及测试。
