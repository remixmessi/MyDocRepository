# 桌面签名、公证与更新

客户端默认使用 GitHub 正式 Release 进行应用内检查、下载和重启安装，也保留 Web 版本维护与手动下载。普通 `desktop:dist:mac`／`desktop:dist:win` 仍生成本地开发包。正式构建与本地打包分开，避免缺少证书时误产出“正式”未签名包。

## 正式构建

在对应平台运行，先提供环境变量，再执行：

```sh
# macOS：Developer ID Application 证书与 Apple 公证凭据
corepack yarn desktop:release:mac
# Windows：代码签名证书与发布者名称
corepack yarn desktop:release:win
```

两条命令先检查配置，再构建并调用 electron-builder；固定 `--publish never`，只输出 `release/desktop/`。macOS 构建 arm64 与 x64 的 DMG／ZIP，Windows 构建 x64 NSIS。macOS 最低要求 13.0，所有 macOS 入口在压缩前校验实际 Mach-O 架构。不要把本机 arm64 Electron 的 `electronDist` 传给 x64 构建。依赖下载慢时参见 [桌面打包](./桌面打包.md)。

macOS 环境变量：

| 变量 | 用途 |
| --- | --- |
| `CSC_LINK` | Developer ID Application 的 P12 文件路径或 Base64 |
| `CSC_KEY_PASSWORD` | P12 密码 |
| `APPLE_API_KEY` | 公证 API 私钥 `.p8` 的绝对路径 |
| `APPLE_API_KEY_ID` | API key ID |
| `APPLE_API_ISSUER` | issuer ID |

本地公证也支持 `APPLE_ID` + `APPLE_APP_SPECIFIC_PASSWORD` + `APPLE_TEAM_ID`，或 `APPLE_KEYCHAIN` + `APPLE_KEYCHAIN_PROFILE`。脚本要求证书配置完整，不允许 `CSC_IDENTITY_AUTO_DISCOVERY=false`。正式配置开启 hardened runtime、公证和最小 JIT entitlement。

Windows 环境变量：`WIN_CSC_LINK`（PFX 路径或 Base64）、`WIN_CSC_KEY_PASSWORD`、`MYDOC_WIN_PUBLISHER_NAME`（证书发布者名称，必须与证书匹配）。正式配置强制签名、启用资源编辑、SHA-256 签名，保留更新器的发布者签名验证。

只做配置预检可运行 `node scripts/desktop/release.mjs mac --check` 或 `win --check`；通过不代表已验证证书有效、公证成功或安装运行。

证书、私钥和密码通过本地环境或 CI secrets 注入，不写入源码、文档、安装包或聊天。

## 流水线

`.github/workflows/desktop-release.yml` 仅手动触发，在 macOS／Windows 各自完成类型检查、单元测试、真实 Electron 测试、签名构建和系统签名检查，再保存 Actions artifacts。此签名流程无发布动作、无 Releases 写权限。普通 `.github/workflows/desktop.yml` 负责开发包，并按下述规则关联 GitHub Releases。流水线必需的桌面测试、单元测试、PDF 夹具、Vitest 配置及 Yarn 锁文件纳入版本控制范围，其他浏览器测试继续沿用原忽略规则。

### 自动关联 GitHub Releases

普通桌面流程在推送分支、版本标签（如 `v0.1.1` 或 `0.1.1`）、发布 GitHub Release 时自动运行，也可在 Actions 中手动运行。推送分支、标签、Pull Request 和 Actions 手动运行均只构建并保存 Actions artifacts，不创建 Release，也不上传 Release 附件。只有用户手动发布 GitHub Release 后，才构建并上传对应版本的安装包。

发布前先将 `packages/frontend/apps/desktop/package.json` 的 `version` 设置为目标版本。版本说明可保存在 `docs/releases/<版本号>.md`，创建 Release 时由用户填写。标签必须与标签所指提交的桌面版本一致，目前仅接受 `vX.Y.Z` 或 `X.Y.Z` 正式版本格式，不匹配会在构建前失败。开发分支可提前使用下一版本号；分支推送不会发布该版本。

用户手动发布 Release 触发的三个构建任务（macOS arm64、macOS x64、Windows x64）全部成功后，上传任务汇总 DMG、ZIP、EXE、blockmap、更新清单和 `SHA256SUMS.txt`，合并两个 macOS runner 的 `latest-mac.yml` 并验证其安装包的 SHA-512 与大小，上传到对应标签的已有 Release，保留用户填写的标题、说明及发布状态。重跑此次 Release 工作流会替换同名附件。Release 不存在时上传失败，流程不会创建 Release 或标签。仅保存 Release 草稿不会触发上传。

例如，0.1.1 开发完成并提交后，可运行以下命令推送版本标签（将 `<版本提交>` 替换为实际提交）；这一步只构建，不发布版本：

```sh
git tag v0.1.1 <版本提交>
git push origin v0.1.1
```

随后在 GitHub 的 Releases 页面手动新建 Release，选择 `v0.1.1`、填写说明并点击发布，安装包才会自动构建并附加。当前已发布版本仍为 0.1.0，0.1.1 是下一版本的开发版本号。

发布任务使用仓库自带的 `GITHUB_TOKEN`，仅该任务申请 `contents: write`，无需额外 PAT。此流程生成的仍是开发安装包；正式分发和 macOS 应用内安装所需的证书签名、公证需按本文其他章节配置。若标签已发布且指向旧提交，应先确保该提交包含新的工作流；手动重跑旧版本工作流不会自动获得后续提交中的改动。

GitHub Actions 配置：

- Secrets：`MAC_CSC_LINK`、`MAC_CSC_KEY_PASSWORD`、`APPLE_API_KEY_BASE64`（原始 `.p8` 的 Base64）、`APPLE_API_KEY_ID`、`APPLE_API_ISSUER`、`WIN_CSC_LINK`、`WIN_CSC_KEY_PASSWORD`。
- Variables：`MYDOC_WIN_PUBLISHER_NAME`；如使用自建 HTTPS 更新渠道再提供 `MYDOC_UPDATE_URL`。
- macOS 私钥临时写入 runner 临时目录，步骤结束删除；签名后执行 `codesign`、`stapler`、`spctl` 检查。Windows 检查应用及安装程序的 Authenticode 签名状态。

尚未配置凭据，不应把本地未签名包、预检或交叉打包成功写成正式签名验收。当前未触发远程流水线。

## 更新机制

侧栏、统一命令面板和桌面“帮助”菜单均可打开“版本与更新”。主区域显示当前版本、运行架构、GitHub 应用内更新和服务器检查；配置自建 HTTPS 更新渠道时，其操作放在下方折叠区。自动检查偏好独立保存在用户数据目录 `update-settings.json`。

### 初始方案：Web 发布与手动下载

服务器管理员进入 Web“设置 → 版本维护”，填写版本号、操作系统、处理器架构、更新说明并上传安装包。macOS 的 **Intel（x64）** 与 **Apple 芯片（arm64）** 分别发布、分别计算最新版本；上传时必须明确架构。安装包保存在云数据库同目录的 `releases/`，备份发布记录时应同时保留该目录。

客户端在“版本与更新”中填写 IP、域名或完整 HTTP／HTTPS 地址，保存后点击“检查服务器版本”。客户端自动携带实际运行的系统和架构请求 `/api/cloud/releases/latest?platform=darwin&arch=arm64`（参数随设备变化）；通过 Rosetta 运行的 x64 客户端匹配 x64 包。最新版本按 SemVer 比较，而非上传时间。检查不要求登录服务器账号。

发现版本后显示更新说明、文件大小与 SHA-256，并提供安装包下载，下载后由用户手动安装。此方式不会自动下载、重启或安装。原有未标注架构的 macOS 发布记录保留在管理列表中，但不参与客户端匹配；需重新上传并选择 x64 或 arm64。

### 应用内更新渠道

macOS 与 Windows 安装版默认使用固定的 GitHub 仓库 `remixmessi/MyDocRepository`；源码开发运行禁用安装。正式构建设置 `MYDOC_UPDATE_URL` 时优先使用自建 HTTPS 目录，也可在 GitHub 区域切换到 GitHub。地址必须为 HTTPS 目录，不接受账号、密码、查询或片段。由 electron-builder 写入 `app-update.yml`；所有更新地址和安装命令由主进程管理，渲染器只能请求检查、下载和安装，不能提交 URL、文件路径或可执行命令。下载中、已下载及安装中不会切换渠道。

启用后默认启动 30 秒后及每 6 小时检查，可关闭自动检查。发现新版本不自动下载；用户下载完成后选择“重启并安装”，也可稍后安装。普通退出不会自动安装。更新器拒绝降级及预发布版本。

安装前锁定编辑并完成所有打开文档、工作区和偏好的保存；随后生成完整 SQLite `before-update` 保护快照，成功后才允许关闭窗口及安装。保存、快照或安装失败解除锁定，保留当前窗口和下载，提供重试。保护备份与恢复前保护备份合计保留最近 3 份，可通过“自动备份与恢复”查看并恢复。安装包不包含用户数据库。桌面端数据库固定保存在 Electron 用户数据目录的 `data/mydoc.sqlite`，不再写入 `.app`、`resources` 或 Windows 安装目录，因此替换安装包不会重置数据。首次运行新版本时，如果用户数据目录还没有数据库，会把旧版本安装目录中的 `data/mydoc.sqlite` 及 SQLite `-wal`／`-shm` 文件迁移过去；目标已有数据库时不会覆盖。NSIS 卸载也保留用户数据，重新安装后仍可继续使用。

未来配置渠道时，将对应平台安装包、macOS ZIP、`latest.yml`／`latest-mac.yml` 和 `.blockmap` 保持原名一起上传到 HTTPS 目录。先上传版本文件、最后替换元数据；构建版本号需高于当前版，正式安装至少两版以验收检查、下载、签名校验、保存失败、备份失败、重启安装及数据库／附件保留。macOS 自动更新使用 ZIP，不能只上传 DMG。发布动作需另行明确授权。

当前交付：更新代码、界面、签名配置与流水线。未完成真实证书签名、公证、渠道下载及两版安装更新验收；Windows 安装运行仍待 Windows 实机验证。

参考：[electron-builder v26 自动更新](https://www.electron.build/v26/docs/features/auto-update/)、[macOS 签名](https://www.electron.build/v26/docs/features/code-signing/code-signing-mac/)、[Windows 签名](https://www.electron.build/v26/docs/features/code-signing/code-signing-win/)。

## GitHub 应用内更新

客户端「版本与更新 → GitHub 更新」提供 **检查 GitHub 版本 → 下载并更新 → 重启并安装**。下载在主进程中进行，显示进度与已传输大小，下载完成后由用户决定何时安装。关闭窗口后重新打开仍可查看当前下载状态。自动检查默认开启，在启动 30 秒后及每 6 小时检查；普通退出不会自动安装。下载、保存、备份或安装失败均可重试。下载更新包会验证更新清单中的校验值，并按系统和架构筛选 macOS ZIP / Windows EXE，不降级、不安装预发布。更新说明以纯文本展示。

发布前修改 `packages/frontend/apps/desktop/package.json` 的 `version`，使用一致的 `vX.Y.Z` 或 `X.Y.Z` 正式标签。打包命令现在默认生成 GitHub 更新配置及清单，本地打包使用 `--publish never`，不会上传。产物位于 `release/desktop/`：

| 平台 | 同一 Release 需要上传的文件 |
| --- | --- |
| macOS | 对应架构的 `.zip`、`.zip.blockmap`（如生成）、`latest-mac.yml`；`.dmg` 供首次安装 |
| Windows | NSIS `.exe`、`.exe.blockmap`、`latest.yml` |

macOS 同时发布 Intel 与 Apple 芯片时，推荐 `corepack yarn desktop:dist:mac`，在同一次构建中生成两个架构并合并清单。不要把两次独立构建的同名 `latest-mac.yml` 直接互相覆盖。GitHub Release 流水线使用 `scripts/desktop/prepare-release-assets.mjs` 合并各 runner 的清单，确认版本一致、ZIP/EXE 齐全、文件大小和 SHA-512 正确后再上传；不会创建或发布 Release。仅上传 DMG 或漏传更新清单的旧 Release 会提示未准备好，不能应用内更新。

macOS 原生更新安装要求有效代码签名，正式分发应使用 Developer ID 签名并公证，当前本地 ad-hoc 包不代表已经完成系统安装验收。Windows 正式签名包沿用发布者签名验证。正式命令为 `corepack yarn desktop:release:mac` / `corepack yarn desktop:release:win`，两者均只构建、不上传。真实两版签名安装升级与 Windows 实机验收仍需相应证书及环境。
