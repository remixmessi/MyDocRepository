# 数据库启动检查与增量升级

Web 开发与预览、独立 Web 服务（含 Docker）和 macOS / Windows 桌面应用共用 `SQLiteProjectDatabase`。每次启动先获取 SQLite 写锁，检查数据库版本，执行缺少的迁移，补建缺失表和索引，再检查所需字段与 `PRAGMA quick_check`。完成后才提供存储服务；浏览器也会在加载工作区前检查服务返回的结构版本。

公共库使用 `PRAGMA user_version`，当前为版本 4：基础业务表、离线队列与草稿、本地账号与会话、附件文件索引。已有请求时创建的账号表通过 `CREATE TABLE IF NOT EXISTS` 接入迁移，不覆盖账号数据。协作库另用 `cloud_migrations` 记录版本，当前为版本 12；版本 5 纳入账户资料与设备会话字段，版本 6 纳入桌面发布架构字段，版本 7 新增全局空间管理审计表和空间／时间索引。版本 8 新增办公资源目录，版本 9 新增办公恢复回执表 `cloud_office_restores`，以工作区、发起人及恢复编号作为主键。回执与新资源在同一事务提交，删除工作区时一并清理；整库 SQLite 快照保留回执，单文件办公备份不携带回执，旧业务备份格式不导入回执。版本 10 新增完整团队工作区恢复回执表 `cloud_workspace_restores`，以发起人和恢复编号作为主键，保存输入文件 SHA-256 与新工作区 ID；回执与全部内容同事务写入。删除恢复出的工作区后保留该回执，重试返回已删除状态，避免旧请求意外重新创建工作区。整库快照保留回执，团队内容备份及旧笔记备份不携带回执。版本 11 新增 `cloud_office_versions` 命名版本表，版本内容、校验值及操作回执同一行原子写入；启动保留校验纳入既有历史记录。版本 12 新增持久导出任务表 `cloud_office_exports`。旧会话缺少公开 ID 时会补全，已有 ID 保持不变。

公共迁移与协作迁移在同一个启动事务内执行，表结构、数据补全和版本号同时提交。公共启动事务会保留业务表原值，协作服务另核对原账号、空间及成员；迁移若删改这些既有记录则报错回滚。任何一步失败都会回滚，关闭连接并阻止启动。Docker 入口在迁移前使用 `VACUUM INTO` 生成包含 WAL 已提交内容的旧结构快照，备份失败不迁移。遇到更高版本数据库时拒绝启动，需要升级程序。已是最新版本的库仍检查结构；缺少已知可补全的协作字段时增量补列，无法安全补全的基础字段缺失时报告具体表名和字段，等待修复迁移或恢复备份。

## 开发新功能

1. 公共表变更在 `packages/common/nbstore/src/schema.ts` 提升版本并追加迁移，使用 `ALTER TABLE … ADD COLUMN` 增加字段，为已有记录提供合适默认值或显式回填。历史迁移保持原样。
2. 更新 `SCHEMA_COLUMNS` 中的列契约与 `SCHEMA_CREATE_SQL` 中的当前建表语句。补建语句只包含幂等建表、建索引，不重放 ALTER 或数据迁移。
3. 协作表变更在 `packages/frontend/apps/web/server/schema.ts` 提升版本，追加迁移及记录，更新字段检查。新增列先检查存在性，兼容旧版本已补过字段的情况。
4. 新增表需要明确备份、恢复规则。当前整库快照包含本地账号、会话、队列和草稿；业务恢复只替换文档、附件和偏好，保留账号及本机未提交状态。旧版本业务备份仍可恢复。
5. 用临时数据库验证升级前后的业务数据、连续多次启动、迁移冲突回滚、高版本拒绝以及备份恢复。不要用真实运行数据做迁移测试。

约束变更需要重建表时，必须在事务内复制全部既有数据并验证，不可直接删除业务表。功能发布前必须包含对应迁移，不能依赖用户删除数据库或手工执行 SQL。

Docker 入口在 SQLite 打开有 WAL 的原库前，先原样归档主库与日志并记录 SHA256，在临时副本上对比主库已有账号 ID。应用 WAL 后丢失已有账号 ID 时，拒绝打开原库，不进行日志恢复、迁移或管理员初始化；原始文件和归档都保留。此检查不修改数据库结构或历史迁移。


## 附件目录迁移（公共版本 4）

`attachments/` 固定在数据库文件同级，适用于桌面端、Web 开发、独立服务与 Docker。`assets` 保留隔离键、名称、类型及兼容旧备份的 `data` 列；`asset_files` 记录相对路径、大小与 SHA-256。运行库的 `data` 在完成文件迁移后保存为空 BLOB，实际字节由文件读取。

每次启动在同一个写事务内完成历史附件迁移与校验。文件按内容哈希分片保存为 `attachments/<哈希前两位>/<完整哈希>`，使用临时文件、fsync、原子重命名与读回校验；写入并校验成功后才更新文件索引和清空原 BLOB。所有附件成功后才推进结构版本。文件写入、校验或结构升级失败时回滚数据库、关闭连接并停止启动；原 BLOB 和原版本保留，修复后重启可重试。已完成迁移的附件缺失或损坏时拒绝启动，不生成空文件顶替。

文件系统不参与 SQLite 回滚：失败可能留下未引用的哈希文件，但不影响原附件；重试可验证并复用。删除附件只移除数据库记录，文件暂保留，以避免影响并发读取和尚在生成的快照，不在本次升级中自动清理孤立文件。重复启动不重复生成附件文件。迁移释放的 SQLite 页可被后续写入复用，数据库物理文件不会立即缩小。

完整备份和服务端升级保护快照会将附件重新嵌入快照数据库并清空快照内的文件索引，仍是自包含的 SQLite 文件。恢复历史版本备份时，在恢复事务内重新生成并校验附件文件后才提交；失败回滚当前业务数据。手工迁移运行库必须停止应用并一起复制数据库及 `attachments/`，不要只复制数据库文件。

## 全局空间管理审计（协作版本 7）

`cloud_workspace_audit` 记录操作者 ID 和名称、目标空间 ID、操作类型、详情及时间。管理修改和审计写入在同一事务内完成；删除空间不删除审计记录。整库快照包含该表，恢复后可继续查询；业务备份与恢复只替换文档、附件和偏好，保留当前审计记录，不从业务备份覆盖管理历史。旧库通过启动迁移新增空审计表，不补造历史操作。

## 团队工作区内容备份（协作版本 10）

`GET /workspace-backup` 仅允许工作区所有者，读取同一事务快照；包含普通正文、目录/回收、模板、全部已接入的办公模型及软删除状态、不可变原件、附件字节与归属、永久删除标记及版本 2 中的命名历史版本。每份最多 50 MB（JSON 含 Base64），单模型 16 MB、单附件 20 MB、共最多 10001 份状态（含工作区目录）、10000 个资源/附件/删除标记。查询先检查存储总量，再读取二进制数据。每份状态和附件包含 SHA-256；这是损坏检测，不能证明备份来源。

`POST /workspace-restore` 在受限子进程中校验及重映射，恢复为当前账户独占的新团队工作区。新工作区命名空间内保留文档、资源和附件 ID；目录状态键和内部引用改为新工作区 ID，办公 generation 重新生成，原操作回执清空。成员、权限、会话、个人 UI、离线队列、历史恢复回执不复制；跨工作区引用仍指向原外部目标，不复制外部内容。工作区、文档、原件索引、资源归属、删除状态和恢复回执在同一数据库写事务提交；文件写入失败或任一 SQL 失败回滚，可能留下未引用的哈希文件，重试可复用。

同一账户、恢复编号及输入文件哈希的并发/重试返回同一新工作区；同编号换文件返回 409；已恢复工作区被删除或所有权改变后返回 410。恢复编号在当前弹窗中保留，浏览器刷新后重新选择会开始新任务。校验和导出等待期间再次检查账户、会话、所有者权限及目标存在性。旧 `.mydoc.json` 笔记备份仍使用原本本地恢复路径；新 `.mydoc-team.json` 恢复到团队服务器，不覆盖本地或已有团队工作区。

## 办公命名版本（协作版本 11）

`cloud_office_versions` 保存工作区、源资源、版本 ID、名称、保存/导入者、操作编号、时间、内容 BLOB、SHA-256 和删除标记，主键为工作区/资源/版本，工作区/资源/发起人/操作编号唯一；另建工作区/资源/删除状态/时间索引。版本 10 的数据库在同一个启动写事务中建表、建索引及推进版本，既有资源、文档、账号和偏好不变。重复启动不重放迁移；失败回滚，较高版本库拒绝启动。

命名版本只固定保存当时已确认的受支持模型和原件，采用现有单文件办公备份契约，服务端隔离校验后持久化，不是格式兼容性的扩展。单资源最多 100 个有效版本；工作区版本内容总量 200 MB、包含删除回执的记录最多 10000 行。容量满时需清理或迁移新工作区，不自动删除旧版本。删除版本释放 BLOB 并保留操作编号，旧保存请求重试返回 410，避免复活；损坏的版本内容也允许有权限的用户清理。工作区删除时清理全部历史行；软删除文件保留其历史，管理员可分页查看并恢复已保存版本。

`POST /office-versions` 按文件编辑权限保存命名版本，同编号/名称返回原结果，即使当前文件后来发生变化也不重新捕获；同编号改名拒绝。`GET /office-versions` 与 `/office-version` 按源文件阅读权限列出或下载；下载校验 SHA-256。删除只允许作者或管理员，且仍需源资源编辑权限。已删除文件仅所有者和管理员可查看/管理其历史，不能创建新版本。

`POST /office-version-restore` 校验后恢复为新的资源/原件 ID 与 generation，复制创建时源文件的资源级权限，模型及权限在同一事务提交。当前文件不回退，旧离线队列不会指向新副本；重复恢复返回同一副本，不重新改写副本后来的权限。源文件历史仍归源文件，新副本不复制整套历史。此路径不代表已完成同一资源原位回退或旧代际队列拒绝协议。

团队完整备份升级为 `mydoc-team-workspace` 版本 2，新增 `versions` 数组：包括有效历史版本的归属、名称、时间、内容及哈希，不包括原操作编号、删除回执或原成员身份。原件和模型嵌入版本内容，全部仍受整包 50 MB 配额约束；历史过大时明确拒绝，不静默遗漏。恢复时先隔离校验全部历史模型、格式、归属及原件一致性，再与新工作区一起原子导入；版本管理者归当前恢复账户，原时间保留。版本 1 团队备份和旧本地笔记备份仍可读取；旧程序需升级才能识别版本 2。整库物理备份保留全部历史及删除回执，单文件办公备份仅包含一个固定模型与原件，不含整套历史。


## 办公持久导出任务（协作版本 12）

`cloud_office_exports` 保存工作区、源资源、任务 ID、发起人、操作编号、格式与范围、工作表、状态（queued/running/done/failed）、创建与完成时间、固定快照 SHA-256、输入快照、产物、产物 SHA-256、字节数、文件名、MIME 及失败原因；主键为工作区/资源/任务，工作区/资源/发起人/操作编号唯一，另建工作区/资源/时间及状态/时间索引。版本 11 的库在同一个启动写事务中建表、建索引并推进版本，既有资源、版本、文档、账号和偏好不变；重复启动不重复记录版本，迁移失败回滚，更高版本拒绝启动。建表语句幂等，已是版本 12 但缺表时补建。

任务创建时在同一事务内读取已保存状态并固定输入快照，之后的编辑不影响产物；完成后清空输入、只留产物。服务启动时把残留的 running 任务改回 queued 重新执行，不恢复进程租约；解析进程繁忙时任务重新排队而非失败。每个文件保留最近 20 条记录、最多 5 个进行中任务，工作区产物共 200 MB，超出时删除最早完成的记录；单个产物上限 50 MB。直接下载的兼容副本同样登记为已完成任务。下载按源文件阅读权限，并校验产物 SHA-256；删除仅限发起人或管理员。删除资源后不再列出，删除工作区同时清理。

备份规则：导出产物可由当前内容重新生成，不属于业务数据。团队完整备份与单文件备份不携带此表；个人物理备份在生成快照时清空此表，恢复时清空当前导出记录。个人物理备份扩展把该表声明为可选，协作版本 11 的旧个人备份（没有此表）仍可恢复，恢复后下次启动由迁移补齐版本 12。整库快照（Docker 升级保护）原样保留该表。

## 协作通知与编辑记录（协作版本 13）

新增两张表，不修改既有表（个人物理备份按精确列清单校验，新增列会使旧备份无法恢复）：

- `cloud_notifications`：办公评论中的 @提及（`mention`）与回复参与讨论（`reply`）通知，按用户保存，每人最多 500 条，超出删除最早的。列表时按当前成员身份和文件访问权过滤；失去权限只隐藏不删除，恢复权限后重新可见。文件删除后不再列出，删除或清理工作区时一并删除。
- `cloud_office_activity`：办公文件编辑记录。同一成员 10 分钟内的连续保存合并为一行（`started`/`last`/`edits`），每个文件保留最近 200 行。记录失败不影响已接受的编辑；评论不计入编辑。

通知与评论状态在同一写事务内提交，重复提交同一评论操作编号不会重复通知。迁移 `version<13` 只建表并写入版本记录，与其他迁移处于同一启动写事务；之后的幂等建表语句会补回缺失的表。

备份规则：两张表都是协作派生数据。团队完整备份与单文件备份不携带；个人物理备份在生成快照时清空，并在扩展中声明为可选，因此协作版本 11、12 的旧个人备份（没有这两张表）仍可恢复，下次启动由迁移补齐版本 13。整库快照（Docker 升级保护）原样保留。

验证：版本 12→13 升级保留导出任务与审计记录、失败回滚到版本 12 且不留新表、重复启动不重复写版本、缺表自动补回、拒绝更高版本；个人物理备份不含通知与编辑记录，版本 12 与版本 11 的旧个人备份均可恢复并在重启后升级。

### 个人办公文件存储接入（2026-10-19）

个人桌面与开发 SQLite 入口通过 `SQLiteProjectDatabase(..., upgradeCloudDatabase)` 在原有启动写事务内建立并检查现有办公结构。未增加数据库版本或改写历史迁移；公共版本 4、协作结构版本 11。生产网页复用已经升级的当前服务数据库，按 `user:<account>` 与个人工作区派生办公命名空间；桌面使用本机 `main` 存储范围。不会创建云账号/成员/团队行。

`CLOUD_SCHEMA_COLUMNS` 复用启动检查的列契约。仅个人数据库声明 `LOCAL_OFFICE_BACKUP` 物理备份扩展，允许并校验完整的当前办公结构，拒绝包含团队账号/会话/团队数据的快照。完整恢复在一个写事务中替换办公表和原有业务表，迁移附件并更新代际；失败整体回滚。旧的仅笔记快照没有办公表时，恢复清空当前办公内容但保留当前迁移版本。团队数据库仍沿用团队备份恢复契约，不通过此扩展恢复。

验证覆盖旧库增量升级/原数据保留/重复启动/迁移失败回滚/高版本拒绝的既有启动测试，以及个人办公服务与数据库关闭重启、原件字节保留、旧个人备份恢复、完整物理备份往返、账户/工作区隔离、恢复期间和旧代际请求拒绝。
